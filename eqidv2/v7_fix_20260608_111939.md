## Required Timing Contract

This is the selected V7 execution contract:

```text
Signal candle:       10:00:00
Intended execution:  10:01:00
Final deadline:      10:01:30
Execution price:     live LTP/fill available between 10:01:00 and 10:01:30
```

Contract rules:

1. `intended_entry_ist = signal_time_ist + 1 minute`.
2. `deadline_ist = intended_entry_ist + 30 seconds`.
3. The signal must pass discovery, post-filters, entry checks, risk checks, and reach the executor by `deadline_ist`.
4. Paper and live must enforce the same deadline.
5. A signal detected, handed off, or executed after `deadline_ist` is rejected with an explicit reason.
6. Missing or unparseable timing fields fail closed. `lag=None` must never pass freshness validation.
7. The forming 10:01 one-minute candle is not required and must not be treated as a completed bar.
8. Do not substitute `signal_close` and label it as the execution price.
9. Actual execution price is the live LTP or broker fill captured during the allowed 30-second window.
10. No setup-specific exception may extend the final deadline beyond 30 seconds.

Required aligned values:

```text
ENTRY_LAG_MIN=1
ENTRY_DUE_GRACE_SEC=30
MAX_SIGNAL_HANDOFF_LAG_SEC=30
LATE_DETECTION_MAX_LAG_SEC=30
```

The configured scheduler grace may reserve a small processing allowance before
the hard deadline. For example, a 30-second configured grace with a 2-second
processing reserve produces a maximum candidate-wait budget of 28 seconds. The
hard row-level `deadline_ist` remains T+1:30.

#### C1 - Remove the forming-bar requirement ✓ Applied 2026-06-08

`eqidv2_entry_engine_1min_v5_id.py:889` — When `_entry_bar_for_candidate` returns None, the candidate is no longer dropped. The signal-bar close is used as the SL/TGT geometry reference (not as the execution price). `entry_bar_source` is written to the `diag` field (`forming_t1_open_reference` when the T+1 bar is present, `signal_bar_close_reference` when absent). Executor uses live LTP for actual fill.

Current-minute availability from historical-data APIs is not reliable: June 8 SKYGOLD returned a forming T+1 bar, while other runtime fetches exposed only completed bars.

Do not replace the missing bar with `signal_close` as the execution price.

Separate feature-bar eligibility from entry-reference eligibility.

**Momentum and indicator bars**

- Use only completed, causal bars.
- Require normalized `bar_end_ist <= intended_entry_ist`.
- Never use the high, low, close, volume or indicators of the forming
  intended-entry minute.
- Preserve the completed one-minute interval between signal close T and
  intended execution T+1 when it is part of the existing pre-entry momentum
  design. Do not move the cutoff back to T without replay, because that changes
  the filter.
- Normalize provider timestamps into explicit `bar_start_ist` and `bar_end_ist`.
  The 5-minute signal files are treated as end-labelled while Kite minute
  candles may be start-labelled; raw `date` comparisons are otherwise
  ambiguous.

**Entry reference**

- The actual execution price is live LTP/broker fill.
- If Kite returns the intended-entry minute while it is forming, only its
  immutable opening price may be used as an optional strategy reference.
- Do not use that forming bar's high, low, close, volume or indicators.
- Record the source as `forming_t1_open_reference`.
- If the intended-entry bar is absent, do not drop the candidate. Continue to
  the executor with live LTP and a reference source that the setup's tested
  risk-geometry policy supports.
- Never describe a forming-bar open as a completed candle or as the actual fill.

#### C4 - Overlap discovery and entry waiting

Runtime evidence showed an 11:35 candidate being created at about 11:36:17 after the entry engine had already stopped waiting around 11:36:10.

Additional June 8 evidence for slot 12:05:

```text
feed ready:           approximately T+55s
main V7 scan:         29.7s
Tier123 branch:       51.0s
discovery completion: T+107s (12:06:47)
hard deadline:        T+90s  (12:06:30)
```

The fixed `POST_SLOT_DELAY_SEC=75` BAT value is bypassed while the feed gate is
enabled, so it did not cause this 12:05 delay. It is still an unsafe fallback:
if the feed gate is disabled, a fixed 75-second sleep makes T+1:30 effectively
unreachable. Remove the fixed fallback or set it to zero and require the
authoritative feed gate in production.

The real bottleneck is cumulative feed-ready plus scan latency. With feed ready
at T+55, only 35 seconds remain for discovery, entry checks, writing, executor
receipt, quote and execution. Optional branches must not hold the production
candidate handoff past the deadline.

Required flow:

```text
completed 5m slot
  -> authoritative feed-ready marker
  -> discovery starts immediately
  -> filters run as candidates become available
  -> slot-specific candidate artifact/event is published atomically
  -> entry engine consumes it immediately
  -> executor waits for/reads live LTP
  -> execute only during T+1:00 through T+1:30
```

Avoid duplicate full-universe reads between scanner stages where the same data can be passed in memory or through a slot-specific manifest.

Required latency behavior:

- Publish production-core candidates as soon as their mandatory filters finish.
- Run optional Tier123/shadow branches independently; do not wait for them
  before publishing production candidates.
- Enforce a branch deadline based on remaining time, not only its start time.
- A branch started before its threshold must still be cancelled/ignored if it
  cannot publish before the slot deadline.
- Record feed-ready, scan-start, mandatory-scan-complete, handoff and executor
  timestamps separately.

## Final Verdict

The selected behavior is:

```text
Signal candle:       10:00
Intended execution:  10:01
Final deadline:      10:01:30
```

This cannot be made reliable by renaming timestamps, waiting for the forming 10:01 candle, or using `signal_close` as a fake execution price. The system needs an overlapping discovery/handoff path, authoritative feed readiness, live-LTP execution, and one hard deadline shared by entry, paper and live executors.

Until these changes are implemented and verified, V7 is suitable for paper observation only and is **not live-safe for real orders**.
